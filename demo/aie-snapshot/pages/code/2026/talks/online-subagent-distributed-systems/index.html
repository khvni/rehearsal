Sub-Agents Are a Distributed System (And Nobody Gave You a Consistency Model)

An orchestrator delegates work to several agents.

Girish KondaMicrosoft

Day 1 livestream · 6:37:54–7:00:53 on YouTube. The player starts and stops at this session’s boundaries.

Introduction#

An orchestrator delegates work to several agents. They read a shared repository, conversation, or memory store, call tools against real systems, and return results for the orchestrator to combine. Girish Konda's opening observation is that this already has the structure of a distributed system. Calling the workers “agents” does not remove partial failure, stale reads, duplicated effects, or overloaded dependencies.

Konda, a principal software engineer at Microsoft, explicitly presents his own views and his own design rather than an employer standard. His proposed SAFE handoffs are intended for agents that touch real systems under a single orchestrator. He spends as much time on what the design cannot guarantee as on what it can.

6:41:02 ↗

A fluent answer is not a failure detector#

At 06:41:02, Konda distinguishes an ordinary crash from a more difficult failure: a worker that only partly completed its assignment but returns confident text. Three workers might all classify an alert as benign even though one checked telemetry, one recognized a familiar title, and one did no useful investigation. A conclusion and a confidence score do not reveal which path occurred.

A timeout is similarly ambiguous. The worker may still be running, may have crashed, or may have completed work whose reply was lost. Konda connects this to the distributed-systems distinction between knowing a process failed and suspecting it failed. In his MCP Pacemaker bridge, a server's first-run download could exceed the ordinary timeout while remaining healthy. Conversely, a timeout could obscure the exit code of a server that had actually crashed. The fixes preserved separate initialization timing and the real failure cause.

His first operational rule is to make failure a value: report what was done, what was not done, the evidence, and any side effects. “Could not check” is different from “checked and found no.” Collapsing those states changes retry behavior and the audit trail.

6:47:48 ↗

Three copies of a guess are still one guess#

Konda next describes an agent writing an unmeasured claim into shared context: an error rate fell by 80%. Two other workers reuse it in a review and a runbook. When the orchestrator merges their artifacts, their agreement looks like corroboration, but all three depend on one unsupported sentence.

This is his analogy to a dirty read. An inference becomes visible before anything establishes it as a fact. Asking more workers does not create a quorum guarantee if they read the same unverified source. The relevant question is provenance, not the number of voices repeating the claim.

At 06:47:48, he introduces SAFE: sourced reads, at-most-once effects, fan-out budgets, and explicit outcomes. He does not claim to provide global linearizability for agent reasoning. The aim is a narrower, enforceable handoff discipline.

Original stream, 6:48:20. The slide specifies source, version, as-of time, and revision, and explicitly labels this as Konda's model rather than a universal one.

Sourced reads and effects with identities#

A fact becomes a record with a source, version, scope, and relevant times. Konda distinguishes when the data was current, when it was read, and when it was used. A five-minute freshness policy can accept a decision at 9:07 based on data current at 9:05 and reject reuse at 9:15. Freshness is checked at the decision, not merely when the original worker fetched the data.

Effects require a different kind of record. Suppose a worker creates a pull request, but its reply disappears. Retrying the whole assignment may create another pull request. The outcome is unknown, not necessarily failed. Konda's bridge may replay initialization against a restarted server, but it does not replay an uncertain tool call simply to restore a session.

The proposed discipline gives each effect an identity and binds approval to the exact action. After submission, the system reads back the result by that identity. Submission is not confirmation. A paused worker also must not wake up with stale authority and act as if nothing changed. Konda borrows the idea of fencing tokens: authorization is checked at the execution gate rather than remembered only in a prompt. This is a design requirement, not a claim that every remote API already supports deduplication.

6:54:37 ↗

Concurrency is a resource, not a personality trait#

At 06:54:37, Konda describes concurrent server starts contending over a shared package-manager cache. Each request was individually reasonable; their concurrency caused failure. His response includes a cold-start gate and a session cap, with bounded waits and explicit refusal behavior.

He is unusually specific about the tradeoff. One gate eventually permits progress after a timeout because a permanently hung request would be worse than the cache risk in that case. Other limits refuse work. These are deliberate availability choices, not a promise that one queue configuration makes every operation safe. Capacity must also be reserved before starting work, otherwise queued starts can all observe space and exceed the cap.

Explicit outcomes complete the design. The orchestrator checks schemas, evidence, freshness, and arithmetic in code. A worker claiming that errors fell from ten to six has not demonstrated an error-rate improvement if request volume fell from one thousand to six hundred: both rates are 1%. A failed check should produce a refusal with a reason, not a confident answer with a warning paragraph underneath.

Know what SAFE does not buy#

Konda closes by limiting the claim. Provenance makes a fact checkable, not necessarily true. A lost reply remains unknown until read-back establishes what happened. Partial work does not roll itself back; compensation needs its own design. The model provides no global ordering across independent workers, and it assumes one orchestrator rather than a peer-to-peer collective.

The overhead may be unnecessary for a worker that only drafts text for a person to review. For agents changing production systems, however, Konda wants the handoff treated like a network call: it can fail halfway, arrive late, or be repeated. The useful improvement is not a more reassuring instruction to “be careful.” It is a protocol that can represent partial, stale, and unknown outcomes, backed by checks the worker cannot simply talk its way around.
