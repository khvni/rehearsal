The Rise of the Agent Workforce: Rethinking Agent Infrastructure

Introduction#

A broken data pipeline invites several plausible explanations. Perhaps an upstream job changed. Perhaps the data no longer matches an assumption. An agent can suggest each theory, but testing it against production may be the very thing an engineer cannot safely let it do.

Ankit Mathur's infrastructure proposal is to give the agent a copy of the relevant world. Branch the data and working state, let several investigations run, and bring back tested findings rather than a paragraph of possibilities.

2:50:41 ↗

Exploration needs somewhere realistic to happen#

Mathur starts with chess as an example of computers exploring possible decisions effectively. The broader analogy is search: hard engineering problems often have several paths, and progress comes from trying them, evaluating results, and continuing from what works.

Running several coding sessions gives an engineer more parallelism, but it does not automatically provide a faithful environment for testing their ideas. A branch of the source code may be only a small part of the system. Data, service state, permissions, conversation history, and local files can all affect the result.

At 02:50:41, Mathur proposes investing in realistic simulations rather than relying entirely on a growing inventory of isolated tests. He also raises post-merge verification as increasingly important when changes land rapidly enough that an early branch quickly becomes stale. Neither proposition makes pre-merge checks unnecessary; it identifies what those checks alone may fail to represent.

Branch the pipeline, not just the suggested fix#

Databricks' pipeline example gives the proposal concrete stakes. A partially broken pipeline may already have made writes. Trying a repair directly on production can have consequences beyond whether the agent's code compiles.

Mathur describes branching tables, compute, and governance so an agent can investigate changes in an isolated environment. One branch can test an upstream hypothesis while another tries a different explanation. Each gets a place to rerun work and examine the result.

The change in output is important. Previously, an LLM might hand a person a theory, leaving the risky experiment to the person. With a faithful branch, the agent can return evidence from the experiment. The safety and usefulness of that evidence depend on which parts of reality the branch actually reproduces.

2:58:30 ↗

Conversation, memory, and files all need isolation#

The platform starts with a branchable database. An agent branch may inherit the conversation that led to the investigation, but a new reply in that branch should not silently alter the original agent's conversation.

Memory creates a related problem. Agents accumulate notes from conversations and from explicitly saved findings. Those notes can conflict, become stale, or reflect only one branch's assumptions. Mathur describes offline consolidation that identifies conflicts and distills shared knowledge. Branching lets a proposed memory remain local while it is still being explored, rather than immediately teaching every other agent an untested conclusion.

The database mechanism he outlines separates compute from storage and uses copy-on-write branching. Branches share history while isolating subsequent writes. That saves the need to eagerly duplicate the entire past for every new direction.

But database state is not the whole workspace. Agents also write plans, scripts, and notes to local files. A fresh sandbox without those files loses part of the investigation even if it receives the conversation.

The 2:58:30 source slide makes the isolation concrete: both branches inherit notes.md and plan.md, while A can add findings without rewriting B's workspace.

Mathur describes syncing between local and remote storage to preserve normal file performance while supporting branches. The goal is the entire working state: enough continuity that a new agent can proceed immediately, with enough isolation that a speculative change does not contaminate another investigation.

3:00:00 ↗

Security investigations are a parallel-search workload#

The closing example concerns unexpected outbound network traffic. An initial agent assembles an incident timeline. From there, separate agents can investigate whether a recent deployment introduced an integration or whether a compromised identity is accessing data.

Both begin from the same evidence. Each can gather new evidence and test a theory without mixing its tentative conclusions into the other's workspace. Where the actual service can also be branched, the agent can investigate behavior in a more faithful copy.

This is not a claim that copying an agent makes arbitrary actions harmless. An external system that remains shared can still be changed. Mathur's strongest version depends on branching the parts of the environment the experiment will touch.

The final architectural question is therefore specific: what must be copied for an agent to explore freely without changing the system it is diagnosing? A source-code branch is a start. Conversation, memory, files, data, and services determine whether the branch is a realistic place to work.
