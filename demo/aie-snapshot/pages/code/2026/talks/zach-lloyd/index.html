Software Engineering Is Becoming Factory Engineering

Running several coding agents on a laptop changes how much work one developer can attempt.

Zach LloydWarpFounder & CEO

Day 2 livestream · 1:01:22–1:19:24 on YouTube. The player starts and stops at this session’s boundaries.

Introduction#

Zach Lloyd, founder and CEO of Warp, describes a software factory as a system whose behavior can be measured, changed, and tested like other engineering infrastructure.

Running several coding agents on a laptop changes how much work one developer can attempt. It still leaves that developer supplying the prompts, choosing the tools, and noticing when something goes wrong. Multiply that arrangement across a company and the platform team inherits many different models, skills, security settings, and definitions of success.

Lloyd sees three limits in that setup: human prompting throughput, inconsistent cost and productivity, and fragmented governance. Moving the same agents to the cloud only solves part of the problem. The useful transition is to a system that can learn from its own work.

1:04:38 ↗

Put the factory under version control#

At 01:04:38, Lloyd defines his target as a code-defined, closed-loop system for measuring and improving cloud coding agents. The components might include shared skills, automated triggers, or agent teammates, but a collection of those components does not yet provide the loop.

The first requirement is a declarative description of how work happens. Which agents exist? What triggers them? Which repositories and tools may they use? How does an incoming issue move through triage, specification, implementation, verification, and monitoring?

Lloyd compares this to infrastructure defined in a Terraform-style configuration. The benefit is more than convenient setup. A code representation can be branched, compared, tested, and rolled back. It also gives a coding agent something concrete to modify when the team asks it to improve the process.

The second requirement is feedback. Work enters from people or automated signals, progresses through the configured stages, and produces evidence about the result. That evidence should inform the next version of the workflow rather than disappear when the pull request closes.

1:09:40 ↗

Record the material needed to diagnose a run#

Lloyd's stack at 1:09:40 makes improvement an explicit layer. A workflow engine moves work, but the lower layers supply the reproducible configuration and evidence needed to assess it.

Lloyd's architecture begins with the factory definition and the records of agent work: conversations, generated artifacts, screenshots, and videos. The records are the raw material for investigating why a task succeeded, failed, or consumed more resources than expected.

Above that sit execution environments and inference. Sandboxes make runs more repeatable and constrain their access. Models and harnesses become variables to test rather than permanent allegiances. Claude Code, Codex, Pi, Warp, or an internal harness may have different strengths on the organization's actual tasks.

Orchestration moves work through the stages. APIs and MCP access let people and other agents use the factory from the places where work already arrives, including issue trackers and team chat. Lloyd treats these integration points as part of the system rather than requiring every request to originate in a dedicated interface.

His demo shows a shared view of ongoing agent activity. Seeing a colleague's live session is useful for collaboration, but his stronger reason for centralizing the records is longitudinal: the team can examine how its agents behave without separately instrumenting every developer's laptop.

1:14:07 ↗

Measure the defect you want to remove#

At 01:14:07, the measurement discussion moves beyond output counts. Cycle time, throughput, cost, and human interactions per pull request answer different questions. A high-volume factory can still consume too much human attention or produce expensive changes that are difficult to review.

Lloyd then adds online evaluations over the saved sessions. Another agent examines completed or ongoing work and scores a particular behavior. His example is redundant tests: an agent may add tests that do not contribute meaningful coverage. An evaluator can identify those runs so the team can inspect the pattern and ask what in the workflow encouraged it.

The score is a diagnostic signal. Its useful output is a question the team can investigate: did the instructions push for quantity, did the agent misunderstand an existing test suite, or is some other process change needed? A general declaration that the factory is getting better would be much less actionable than a measured failure mode.

This is why the new toolset includes evaluations and benchmarks alongside traditional engineering skills. A developer still owns whether the product solves a customer problem. Factory engineering adds responsibility for the system producing the changes.

1:16:12 ↗

Make improvement a proposed change, then test it#

At 01:16:12, Lloyd closes the loop. An agent examines failed scores, looks for recurring causes, and proposes a solution as a pull request against the factory definition.

The sequence matters: recorded work produces an observed problem; the problem motivates a configuration change; that change can be evaluated before it replaces the baseline. The factory being code-defined turns process advice into an inspectable artifact. It does not by itself prove that the proposed change is beneficial.

That is the role of replayable benchmarks. Lloyd argues that model rankings, fashionable skills, and harness recommendations cannot answer the local question without local data. A team should take representative tasks from its own workload and replay them against competing configurations. The experiment might change a model, switch a harness, remove a skill, or alter the workflow while comparing cost and quality.

The resulting tradeoff chart is useful precisely because the tasks are the organization's own. A cheaper configuration that loses important behaviors is not necessarily an improvement; a more capable one may justify its cost on some tasks and not others.

Lloyd reports that Warp uses this cycle continually to improve throughput and reduce costs, without offering a universal gain for other organizations. His invitation is to treat agents as a new engineering primitive: establish a baseline, instrument the behavior, diagnose failure, test a change, and keep the improvements that survive contact with the workload.
