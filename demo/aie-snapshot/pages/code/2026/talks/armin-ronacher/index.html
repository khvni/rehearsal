The Software Atelier

Ronacher's coding agent has become much more capable while its core harness has barely changed.

Armin RonacherEarendilCTO

Day 2 livestream · 0:40:03–0:59:29 on YouTube. The player starts and stops at this session’s boundaries.

Introduction#

Armin Ronacher, CTO of Earendil, makes the case for improving the workshop before maximizing the output of the software factory.

Ronacher's coding agent has become much more capable while its core harness has barely changed. Pi still offers the same basic tools, but stronger models need fewer corrections, survive longer tasks, and find new ways to use those tools. If the machine improves without a matching change in the operator, what should the operator optimize?

His answer starts with the workshop. Better power tools let an artist attempt more demanding work; they do not require the artist to maximize the number of objects produced. A software atelier can use agents to pursue quality, coherence, and ambition before trying to become an unattended factory.

0:41:07 ↗

The harness stayed still while the models moved#

At 00:41:07, Ronacher describes Pi's relatively stable core. Behaviors that once needed special prompting or plugins increasingly appear in the model itself. He offers his experience with an autoresearch plugin as an example: a sufficiently capable current model can pursue the optimization goal without the extra machinery he previously found useful.

He then examines his own sessions. Corrections and aborts fall as models improve. Long task runs become much longer. Tool-use preferences change too, with greater reliance on Bash despite no corresponding change in the tool inventory. These are observations from his usage, not a controlled benchmark of all coding agents, but they expose a practical problem: a familiar interface can acquire substantially different behavior after a model upgrade.

The operator should therefore reassess how the system is used, not assume that an unchanged harness implies an unchanged workflow.

0:46:45 ↗

Starting projects scales faster than caring for them#

Human attention has not followed the same improvement curve. Ronacher's agents spend more time working while the number of prompts he sends remains comparatively stable. The machines can expand the work behind a request. They cannot manufacture a corresponding amount of sustained interest in every project that request creates.

The source graph at 46:45 ends at 141 projects started, while the monthly bars for projects worked on for five or more days remain much smaller. These are Ronacher's own repositories, not an industry estimate.

That difference is easy to overlook during the excitement of a new model. Beginning another repository is cheap. Returning to it, using it, and deciding what deserves attention still competes with everything else in a person's life.

Ronacher recounts a friend who automated issue handling and changes for an open-source project, then eventually switched the system off. The project no longer mattered enough to justify using the available inference budget on it. Even an automated project depends on someone deciding it is worth maintaining.

The increased activity also lands on systems outside the agent's immediate environment. Git hosting and older websites may receive much more traffic because agents have discovered new uses for them. Multiplying an individual's productivity can multiply pressure on shared infrastructure that was not designed for the new volume.

0:48:05 ↗

Interrupt before the result becomes expensive to understand#

At 00:48:05, Ronacher identifies an essential workshop skill: knowing when to push back. An agent can satisfy a local goal while adding complexity that makes the overall product worse. A pile of completed feature requests does not necessarily form a coherent application.

He distinguishes skill at operating an agent from knowledge of the engineering problem. Two people can use the same system and receive very different results because one recognizes bad tradeoffs earlier. This knowledge matters even when the person is no longer reading every changed line. Without it, a team can end up asking an agent questions about a system that nobody in the room understands well enough to challenge.

One adjustment in his workflow is to request an explanation before the final verification phase. Rather than wait for a large completed change, he asks the agent for a short executive summary in a readable HTML page while there is still time to redirect it. The purpose is to preserve a useful point of human comprehension inside a longer autonomous run.

That is a pacing decision. The fastest rate of code production may exceed the rate at which the owner can understand the consequences. A good workshop has places to inspect the work before it disappears under the next layer.

0:51:17 ↗

Reimplementing a format does not create agreement#

Agents make it easier to write code yourself and reduce dependencies, a development Ronacher welcomes. At 00:51:17, he also warns about Wildwuchs: uncontrolled growth.

The danger becomes obvious at the edges between programs. Multiple implementations of an archive format can interpret the same bytes differently. A collection of personalized image editors is less useful if their files can no longer be exchanged. An agent can implement a specification quickly, but it cannot remove the need for people to agree on what the specification means.

Forking can feel cheaper than collaborating upstream, especially when an agent can implement the desired change immediately. The cost moves into future interoperability and duplicated maintenance. Ronacher asks engineers to recognize when a problem calls for agreement with other people rather than another isolated implementation.

His preference for excellent software includes faster, smaller, memory-safe systems and exploration of verified software. These are valuable ambitions for the new tools. They also rely on knowledge and shared infrastructure built before agents arrived.

0:55:03 ↗

Long-running agents need a different runtime#

The last part of the talk moves from human pacing to runtime design. A task lasting a couple of minutes can be restarted manually after failure. Thousands of overnight tasks cannot depend on that habit.

At 00:55:03, Ronacher argues for agents and workflows that can stop, suspend, restore, and continue. This is also an economic concern. If cheaper inference scheduling means waiting for tokens, keeping an otherwise idle sandbox fully allocated wastes another resource. The workflow should be able to suspend the surrounding execution while the model is unavailable.

Code mode supplies a second opportunity. Instead of forcing every tool interaction through a fresh language-model turn, the agent can write a program that orchestrates calls, combines their results, and makes decisions. Ronacher describes combining that approach with fast decision models for workloads such as routing thousands of customer requests. The language model creates the workflow; cheaper classification handles repeated branches inside it.

The atelier is therefore not nostalgia for manual coding. It is a place to decide which parts need human understanding, which parts benefit from a better model, and which parts should become ordinary efficient computation. Ronacher closes by asking for software that is more enjoyable and ambitious, rather than treating the ability to build everything as an obligation to do so.
