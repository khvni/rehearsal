I deleted 90% of my harness (And It Got Better)

An agent can reach the right answer while taking an unnecessarily expensive route. Philipp Schmid's harness experiments focus on that difference: two systems may look equivalent in an accuracy table, yet consume very different numbers of turns, tokens, and dollars to finish the same work.

The surviving opening briefly discusses newly available Gemini models and a decision API. Schmid then turns to the more lasting engineering question: which parts of the scaffolding still help as the model becomes more capable?

2:22:45 ↗

A task reward does not prescribe a sequence of tools#

Schmid's post-training sketch contains a task, a model, tools, an environment, and a verifier. The model receives feedback on the result. There is not necessarily one required sequence of tool calls for producing it.

That leaves room for the interface to shape the path. A repository change can be expressed as a series of specialized read and edit operations, or as a short script that makes several related changes together. If each small operation requires another model turn, the specialized path can spend much of its budget returning to the model between steps.

Schmid periodically rebuilds his coding harness to ask what remains necessary. Earlier versions used dedicated tools for editing, planning, and task lists, plus detailed system instructions. His latest experiment pushes the reduction much further: give the agent a shell and see how much work it can organize for itself.

2:25:00 ↗

One tool can expose an entire working environment#

The shell tool described at 02:25:00 runs commands in a clean subshell. It accepts a readable description for the user and supports long-running work: after a timeout, the call returns a handle the agent can use to inspect logs or check progress.

The filesystem supplies other capabilities that might otherwise become separate tools. Plans and memory can be files. Logs can be read later. A command-line agent can invoke another instance of itself. The point is not that planning or delegation stops existing; the model can compose those operations through an interface it already understands.

There is a practical exception. Printing an image file into a terminal produces bytes, not visual input the model can inspect. Schmid therefore evaluates a shell-plus-media variant alongside shell alone and more structured tool sets.

2:29:10 ↗

Equal scores can hide different costs#

The evaluation slide compares four harnesses on roughly 350 coding, terminal, and office-work tasks. Scores fall within about six points, while token usage differs substantially.

At 02:29:10, shell plus media is the table's cost baseline. Shell alone does not win every column: the media-capable variant uses fewer tokens and has a higher cache hit rate in this experiment.

Schmid explicitly notes that he ran each task once. Small score differences could be noise; the table does not establish a statistically reliable ranking on accuracy. It does show why accuracy alone is an incomplete way to choose a harness. Tokens per task, cache behavior, elapsed time, and cost can reveal unnecessary work that a pass/fail result hides.

That qualification also prevents a simplistic conclusion that fewer tools always means a cheaper run. The useful question is whether the interface lets this model accomplish this workload efficiently, including the information it needs to see.

Better models can combine more work into a turn#

The subsequent demonstrations compare model generations and tool configurations. Schmid describes the earlier model using a shell much like a collection of individual tools: one command to read, another to edit, another to continue. Removing specialized tools does not automatically teach that model to batch work.

The more capable model writes an inline script that makes several changes together. It can search selectively rather than reading every file, and combine the resulting edits into fewer calls. In these examples, the benefit of a simpler interface grows with the model's ability to plan and compose operations inside a call.

This is why Schmid argues for revisiting the harness when a new model arrives. A prompt or tool design may have been useful compensation for an older model's limitations. Keeping it forever can force a newer one through a slower sequence it no longer needs.

2:35:00 ↗

Delete deliberately, then measure the route#

Near 02:35:00, Schmid looks toward code-oriented tool interfaces and structured outputs. A model might generate TypeScript or Python that composes operations, with a layer that can inspect those operations more meaningfully than a free-form shell command. He raises security as part of that design, not as something solved by reducing tool count.

The recommendation is an experiment, not a production permission policy: remove scaffolding in an evaluation environment, give the model room to use the computer, and measure what happens. A capable model may work around an awkward harness and still pass the task. The extra turns and tokens tell you what that workaround cost.
