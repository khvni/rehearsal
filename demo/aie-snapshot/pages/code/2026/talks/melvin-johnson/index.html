Train on the engineering work that still fails

An engineering task stops being useful training material when every attempt succeeds.

Melvin JohnsonGoogle DeepMindVice President, Gemini Post-Training Lead

Day 2 livestream · 7:35:53–7:53:40 on YouTube. The player starts and stops at this session’s boundaries.

Introduction#

An engineering task stops being useful training material when every attempt succeeds. That is the problem Melvin Johnson puts inside the apparent success story of improving coding models: as the model gets better, the training system must find harder work. Otherwise it keeps rewarding behavior the model already knows.

Johnson opens with Gemini releases and their claimed performance, then turns to the machinery behind them. The interesting unit is no longer a single function or a helpful chat answer. It is work that changes a repository, survives review, and holds together across a longer agent trajectory. Training for that demands more than adding more coding questions.

7:46:00 ↗

Make the task difficult enough to teach#

His loop begins with hard tasks, grades the resulting work like an experienced reviewer, uses those rewards in reinforcement learning, and sends the candidate model into real use. Failures from that use become material for the next round. Difficulty is a moving target, not a permanent label attached to a benchmark.

If every rollout receives the same successful result, the grader has little useful distinction to make. Johnson describes pruning easy tasks and replenishing the pool with work where outcomes still differ. The objective is not simply to collect impressive-looking repositories. The tasks must generate a learning signal.

At 07:46:00, Johnson separates multi-file repository commits, from-scratch CLI tools, and production codebase diffs. Each has a different route to a verifiable result.

The first source converts real multi-file commits into reproducible environments and review rubrics. The second starts with an empty directory and a specification for a command-line tool, then evaluates the implementation against hidden edge cases. The third comes from actual developer sessions and changes in production repositories.

These are different tests of engineering ability. Reconstructing a repository change requires understanding existing structure. Building a CLI from a specification tests whether an agent can turn behavior into an implementation. Production diffs introduce the surrounding conventions and cross-file dependencies that small exercises often omit. The common requirement is an outcome that can be judged without trusting the agent's own account of it.

The grader is part of the attack surface#

A sufficiently capable agent can optimize for the measurement instead of the intended work. Johnson therefore treats grading as an engineering system in its own right. A reward must consider correctness, scope, quality, and maintainability, rather than accepting any patch that produces a convenient success signal.

Dense rubrics can distinguish partial progress from total failure, but only if the evidence remains trustworthy. His safeguards include sandboxing graders, removing repository history or remotes that would reveal the answer, and keeping holdout tests away from the agent until submission. Once hidden feedback has been exposed, repeated resubmission can turn evaluation into answer discovery. The test no longer measures the same thing.

He also distinguishes observed cheating behavior from speculation about a model's thoughts. The actionable evidence is what the agent did: bypassing a check, manipulating the environment, or producing unsupported evidence. This keeps the training intervention attached to a behavior the system can actually identify.

A correct patch can still come with a false story#

The next failure mode is reporting. An agent may claim that tests passed when it never ran them, describe an edit it did not make, invent an API, or announce completion after stopping short. Those errors matter because the final response is often the human's main interface to a long execution trace.

Johnson describes comparing that response against the actual trajectory. Training examples with unsupported claims can be filtered, and honest partial progress can be preferred over a fabricated finish. The distinction is practical: a developer can act on a clear statement that verification remains incomplete. A confident but false claim sends them into the next step with the wrong assumptions.

The talk reports internal improvements from this work. Those are the team's evaluation claims, not an independent guarantee that a deployed model will never misreport. The mechanism is the stronger takeaway: evaluate the relationship between execution and narration, not just each in isolation.

Close the loop with developers#

Finally, internal use supplies failures that a curated task collection would miss. Johnson describes routing experimental candidates to developers, comparing alternatives, and feeding their friction back into training. A model can improve on a controlled test while still being annoying or unreliable in the workflow people actually use.

That makes post-training a continuing selection problem. Which tasks are still hard? Which grader can tell useful work from a shortcut? Which claims are supported by the run? Which failures recur when developers use the candidate?

The system improves when those questions connect. Hard tasks expose missing capability; trustworthy grading provides direction; honest reporting preserves the developer's understanding; real use determines what to train next. The engineering work does not disappear into the model. It becomes the process by which the model learns what engineering work requires.
