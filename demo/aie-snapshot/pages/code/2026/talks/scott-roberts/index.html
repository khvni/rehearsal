Autocomplete for Actions: System One from the UI to the DB

Introduction#

Workday users do not always arrive with an open-ended research problem. Sometimes they want their pay information, a time-off action, or a colleague's contact card. Scott Roberts asks what happens when an interface can recognize that intent quickly enough to prepare the action while the user is still typing.

6:24:42 ↗

From choosing words to choosing actions#

At 06:24:42, Roberts contrasts quick, concrete tasks with deeper information work. A conventional agent loop can spend several model calls deciding which tool to use and what to do next. That can be disproportionate to the user's request.

His alternative uses Jev for conditional decisions among known possibilities. A deliberately small example asks whether a fish is a pet. Without context the answer is ambiguous; a bowl or a plate changes the relevant probability. The application supplies the question and context rather than training a new classifier for every taxonomy change. Roberts describes decisions fast enough to participate in interactive UI behavior.

Before demonstrating the applications, he states a crucial limitation at 06:28:49: the demonstrations use synthetic data, are not in production, and may never be. They are explorations of what the latency and cost profile permits, not announcements of deployed Workday features.

6:31:56 ↗

A card can form before the question is finished#

Traditional autocomplete predicts more text. Roberts wants it to predict an action surface. As the user types a time-off request, the interface can identify the domain and progressively fill a relevant card. Other examples reveal pay information, assemble a meeting request, or bring up a person's contact details.

The structure is two-stage. First, choose an intent or domain. Then let the team responsible for that domain specify the smaller questions needed to populate its card. This avoids asking one monolithic prompt to understand every product capability and fill every possible field at once. It also provides a place to test collisions: if two cards both appear plausible, the application needs to know that before it ships a new card.

Around 06:31:56, Roberts describes initial experiments with seven cards and a chat fallback, reporting about 96% performance in that limited setup. The fallback is part of the design rather than an embarrassment. The interface does not need a prebuilt action for everything; it needs to recognize the common cases and avoid forcing the rest into the wrong shape.

At sufficiently low cost, the decision can run repeatedly as the text evolves. That changes the interaction from “submit, wait, inspect a plan” to “watch the relevant action become available.” The speed is valuable because it changes when the user receives feedback.

Put the question inside the database query#

Roberts then turns from a single interactive request to a batch of records. His second prototype works with synthetic resumes. Instead of treating semantic matching solely as an embeddings-and-vector-search pipeline, he exposes a model decision through a DuckDB function. A query can ask whether each record matches a natural-language criterion, obtain a score, and order the results.

Original stream, 6:35:20. Roberts changes the question in the query, including a deliberately different plumbing criterion.

The demonstration processes 117 records in about 2.3 seconds of wall time. A machine-learning resume can score highly for relevant trust-and-safety work without scoring highly for plumbing merely because it contains the word “pipeline.” The example is intended to show contextual classification rather than literal keyword overlap.

It remains a small synthetic demonstration. It does not establish that evaluating every record is the right retrieval architecture at arbitrary scale, nor that this prototype is ready to make consequential employment decisions. The mechanism is the interesting part: when a semantic decision is cheap and parallelizable, an ordinary query can use it as a function rather than outsourcing the entire task to a conversational agent.

A new latency budget makes different products possible#

The UI and database examples share a design move. Both keep the surrounding application explicit and insert a model at a bounded decision point. In the UI, that decision selects and fills a card. In the database, it scores records against a criterion. Neither requires the model to invent a workflow from scratch.

Roberts closes on the possibility that fast decisions enable applications which would feel awkward if every judgment required a slow generation. The evidence he offers is exploratory, and he labels it that way. The challenge for an engineer is to find an interaction or batch operation where the cost of waiting has shaped the product, then test whether a narrower decision model can change that constraint.
