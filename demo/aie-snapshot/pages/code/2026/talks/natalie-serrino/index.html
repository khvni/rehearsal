What will you build when AI is 10× faster?

Introduction#

Natalie Serrino, co-founder of Gimlet Labs, asks what happens when agents become fast enough to stay inside an interaction instead of sending us away to wait.

That is the gap between an agent that saves labor and an agent that keeps you in the work. Its usefulness does not establish that it is fast enough.

0:14:11 ↗

Faster changes what feels like an interaction#

To make the difference tangible, Serrino goes back to SquirrelMail. Her comparison runs the same email application with simulated dial-up speeds and with a modern connection. Both versions can perform the task. One asks for much more patience.

Her point is that expectations move. A capability can feel remarkable when it arrives and painfully slow once faster alternatives become normal. It is easy to judge an agent against the time a person would spend doing the whole job. The user also experiences every pause inside that job.

Serrino invokes three familiar response-time thresholds: roughly a tenth of a second feels instantaneous; around one second preserves the train of thought; around ten seconds starts to lose the user's attention. Those are also the distinctions in Jakob Nielsen's response-time guidelines. They are useful design ranges, not a promise that every workload or person has the same tolerance.

A long background task and a direct manipulation interface have different budgets. The question is which kind of experience you could build if the waiting stopped determining the design.

0:17:44 ↗

A token factory has more than one objective#

Producing tokens quickly for one user and producing many tokens across users are different goals. Serrino introduces Token Mint Factory, a game with three ways to score:

  • Minimize latency: get one token out as quickly as possible.
  • Maximize throughput: produce as many tokens as possible in sixty seconds.
  • Meet a deadline: produce as many as possible while keeping each token within a twenty-second service-level target.

The same factory needs different strategies for each objective. A setting that wins on total output may be wrong for an interaction that cannot tolerate a long delay.

Serrino uses player runs to illustrate a latency-throughput frontier: getting faster tokens can mean producing fewer of them with the resources available. Equipment upgrades move the frontier, letting the factory improve more than one objective instead of merely choosing a different compromise.

That distinction matters outside the game. Choosing a point on today's frontier is a scheduling problem. Moving the frontier is an engineering problem.

0:19:23 ↗

Match each piece of the model to the hardware#

At 00:19:23, Serrino describes Gimlet's approach: split a model's work into pieces and run those pieces on different kinds of accelerators. A GPU need not be the best fit for every part.

Moving work between devices adds network overhead. The proposal only helps when better matching the work to the hardware saves more than those transfers cost. Serrino reports that Gimlet can make that trade worthwhile, improving the latency-throughput frontier for the same power footprint. The talk does not supply enough benchmark detail to turn that claim into a general speedup guarantee for every model or deployment.

At 00:20:45, the highlighted horizontal comparison shows faster tokens at the same normalized throughput per power budget. This is Gimlet’s presented comparison, not an independently reproduced benchmark.

The accompanying coding-agent demonstration builds Snake using heterogeneous inference and compares it with a traditional setup. Serrino describes the faster side finishing soon enough to start another change while the other side is still working. The important unit is the completed iteration: build, inspect, ask for the next thing. Faster token generation is valuable when it shortens that loop.

Gimlet's research overview puts this approach in a wider systems program: heterogeneous hardware, low-level kernel generation, and scheduling multi-stage agent workloads. Those are related pieces of work, rather than evidence that changing any single one will automatically speed up an entire application.

0:21:53 ↗

A faster model exposes the next wait#

There is an obvious objection: what if the agent is mostly waiting for tools?

Serrino returns to the slide-editing timeline at 00:21:53. The slide breaks a 105-second turn into 82% inference and 18% tool calls. Its simulation makes inference ten times faster and brings the whole turn to 28 seconds. Tools then occupy 67% of the time.

The source slide at 22:35 keeps tool calls visible as inference shrinks. The lower timeline is a simulation, not a separate measured run.

The user waits for the whole turn. A much faster model cannot make an unchanged tool call finish sooner. Once inference shrinks, work that previously looked like a minor optimization becomes the most valuable place to look.

This is why Serrino moves from fast inference to full-stack optimization. She describes agents using known inputs and expected outputs to verify improvements, and Gimlet's work on self-optimization informed by telemetry from the data center through the model layer. Optimizing a small component in isolation can leave the experience almost unchanged; the measurements need to follow the workload end to end.

0:23:35 ↗

A defender must arrive before the damage#

The most consequential example comes at 00:23:35. Serrino demonstrates a toy dog-photo website with a security agent watching its traffic. The scenario is playful, but she says the application and the underlying node-tar vulnerability are real.

The ordinary upload succeeds. A malicious upload exploits a file-overwrite vulnerability. The defender recognizes that something is wrong, but it is monitoring asynchronously: the damaging action has happened before it can intervene.

In a second run, Serrino uses a faster defender and describes it blocking the malicious request in time. The demonstration illustrates a timing constraint, not a claim that inference speed alone makes an application secure. Recognition after the fact and prevention before the effect occupy different places in the request's life.

The useful question is whether an agent can make its decision within the time the application can afford to wait. If it can, a task designed as background monitoring may become a check inside the live interaction. That architectural possibility is more interesting than shaving seconds off a progress bar.

Design for a latency threshold you have not reached yet#

Serrino ends by asking what much higher token rates might unlock. Her examples include live security decisions, building an application as someone describes it, and completion-like interactions well beyond typing code.

These are directions to explore, not capabilities demonstrated merely by naming a future token rate. Each has a threshold to cross: the maximum delay that still feels conversational, the deadline before a request takes effect, or the pause short enough that a builder keeps iterating instead of leaving.

The closing invitation is to identify that threshold in your own product. What would you put directly in the interaction if you no longer had to design around the wait?
