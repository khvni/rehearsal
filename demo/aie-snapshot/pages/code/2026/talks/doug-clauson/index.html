Introduction#

Doug Clauson, Principal PMT on Kiro, walks through the successive bottlenecks his team encountered as it moved from interactive coding sessions to an agent-operated development workflow.

Few people raise their hands when Clauson asks whether their teams are getting everything they expected from AI. His diagnosis is that many teams have attached an agent to an existing process and accelerated only the code-generation step. The rest of software development still runs at its previous speed.

He contrasts that pattern with an internal Amazon study of teams that changed how they worked. The reported median improvement was 4.5 times normalized deployment velocity against each team's own historical baseline. That is a specific internal measurement, not a promise that installing Kiro multiplies any team's productivity by the same amount. Clauson's talk is about the process changes behind the result.

3:26:05 ↗

Count the work a person can keep moving#

03:26:05

Kiro spans an IDE, CLI, web, and mobile clients. Kiro Crew grew out of an internal effort to run many agents together, then became an open-source product. Clauson's team uses it to build the product itself.

He shows a large and increasing number of merged pull requests, but immediately qualifies what they mean. Roughly one in ten represents a feature. The rest includes tests, bug fixes, and small improvements to existing behavior. Thousands of PRs do not mean thousands of independent new features.

The operating metric he cares about is how many sessions one developer can keep moving. The team's successive increases came when it removed a different reason an agent had to stop and wait for a human.

Five stages, five different ceilings#

The starting point is familiar: one person runs one session, types a request, waits, then responds. Parallel sessions improve utilization, but the person is still the feedback loop for every agent. Running three conversations simultaneously does not remove that bottleneck; it makes the interruptions arrive faster.

Memory and schedules are the next step. Memory carries conventions into a fresh session, while schedules start work without a person manually initiating it. But a schedule on a closed laptop does not help. The team moved to always-on remote machines so work could continue independently of a developer's local session.

That enabled more concurrency, but people still acted as the glue between sessions. An assembly-line workflow reduced those handoffs. Its limitation was nonstandard work. Software tasks do not all follow the same path: a seemingly small issue becomes a larger investigation, a plan needs revision, or an intermediate step fails. A fixed pipeline then waits for someone to repair it.

Clauson's next stage is Ultra Mode, described in the talk as a developer preview behind a feature flag. It places an orchestration agent above the workers. The orchestrator starts work, watches for problems, judges results, decides what to do next, and tries to unstick the process.

He attributes the team's ability to operate more than 50 sessions per developer to this progression. That figure describes its workflow, not a universal capacity limit. He can already see the next constraint: coordinating orchestrators with other orchestrators requires stronger governance and clearer guardrails.

3:34:31 ↗

Replace endless review with a decision process#

03:34:31

The first lesson from the higher throughput is to test everything. Clauson argues that confidence increasingly comes from repeatable checks rather than a person having read every line. That places substantial responsibility on the tests: if they fail to express the required behavior, faster execution only repeats the blind spot more often.

The second lesson is more contentious. The team initially tried to fix every comment from an agent reviewer. Each revision produced new objections, including objections to changes made in response to the previous round. The review loop had no practical stopping condition.

The correction was to distinguish blocking defects from non-blocking suggestions. A broken build must stop a merge. A preference about a variable name need not. That distinction makes review an actionable decision rather than an unbounded invitation to improve everything.

At 3:37:00, the slide shows specialist reviews feeding a single readiness verdict. A failed verdict returns to the prepare-pr repair skill; the review record remains available for inspection.

A fast initial gate checks basic conditions before the slower reviews. Two code reviewers use different model families to reduce shared blind spots. Additional reviews ask different questions: does the design have the right shape, does the change address the actual problem, can a person understand the UX, and does it respect the security posture?

The design review might notice that an existing cache could do the job of a proposed second cache. The UX review might ask whether an error message tells a person what to do next. These are distinct responsibilities, not six copies of “please review this code.”

Each reviewer produces a verdict. A failing result sends the change through a repository skill that attempts to resolve the issue. Humans inspect the review record and whether the process produced the intended result. When that process misses something, the team changes the process. Clauson's account describes a shift in responsibility, not evidence that review errors are impossible.

Teach the system to subtract#

At this speed, adding code becomes easy enough that it can damage the product. Clauson gives agents an explicit responsibility to remove unnecessary machinery, not just introduce more of it.

The same constraint applies to the roadmap. Saying yes to every inexpensive feature can erase a product's shape and overwhelm its users. Implementation cost is no longer a sufficient filter for what belongs in the product. Someone still has to decide what the product is for.

3:38:44 ↗

Keep checking after merge#

03:38:44

A merged PR is not the end of the workflow. The release gate downloads the repository, installs it, runs it, and checks core flows. Security work continues through recurring guidance checks, application-security reviews, and ongoing testing.

Clauson closes by returning to the practical ceilings: human attention, a laptop lid, a rigid pipeline, endless review, and a system that only adds. His team's current answers are not presented as permanent. The point is to notice which constraint is now stopping useful work, remove that constraint, and expect the next one to appear.
