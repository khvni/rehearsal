Introduction#

Complete reading edition, expanded from the official standalone recording. Section links use that recording’s clock. The earlier livestream image is separately labeled.

A pull request widens a column from integer to big integer. CI passes. The registered downstream consumers look fine. Is it safe to merge?

Chetas Joshi uses that apparently harmless change to explain the gap between passing checks and understanding a production data platform. A schema change can be valid locally while breaking a consumer three teams away. Coding agents make those pull requests cheap to open; they do not automatically create more reviewers who know the surrounding system.

The response at Robinhood is a hybrid reviewer with deliberately different responsibilities. Scripts check authoritative facts. An agent searches code and reasons about risks those checks do not cover. People retain decisions that require authority or information neither layer possesses.

0:06:49 ↗

Keep facts out of the model's guessing game#

The first layer queries systems of record. Does the new source column exist in the schema registry? Does the table have an owner? Are personal-information tags present? Do registered consumers tolerate the change? Can the pipeline meet its freshness target under a production-scale staging test using mock data?

A failed deterministic check makes CI red and blocks the change. The agent does not get to explain away a missing required tag because the PR description sounds reassuring.

The limitation is coverage. A lineage check knows only the relationships recorded in lineage. Passing it means that the registered picture looks safe, not that every possible downstream consumer has been inspected.

0:10:23 ↗

Search for the relationship the catalog missed#

The agent layer receives the diff, the author's explanation, and repository tools. It can search beyond changed lines into pipeline definitions and grants. It does not query production state or the live catalog; those facts belong to the first layer or a human investigation.

Original livestream frame at 05:07:15, the missing relationship is visible: an unregistered job reads the widened column even though the lineage tool does not list it.

That job writes into another table whose destination column is still an integer. The change can appear fine until a sufficiently large value arrives. Then the downstream write fails. The reviewer needs to explain the whole path, not merely attach a vague “risky change” label to the widened type.

The repository search has its own blind spots. Ad hoc queries and dashboards may live elsewhere. Joshi insists on a useful reporting distinction: finding no consumers in the searched code is not evidence that no consumers exist.

In the running example, the agent escalates. A human checks that the discovered job is active in production. The remedy is sequencing: widen the downstream destination first, then merge the upstream change. The goal is to make the change safely, not reject it indefinitely.

0:16:49 ↗

Some decisions never become automatic approvals#

For ordinary changes, passing scripts and an approving agent review can be enough. But protected categories always go to a person: sensitive-data grants, migrations that change meaning rather than mechanics, and cases where the reviewer lacks confidence.

This separates two questions often collapsed into a risk score. How risky does the agent think the change is? And is this a kind of decision it is authorized to make? A confident verdict cannot override the second answer.

The review itself should give the person specific comments, the evidence chain, and a reason for escalation. Otherwise automation merely moves a pile of work into a different inbox.

0:20:14 ↗

Improve the rules from explained corrections#

Human replies are collected, and the on-call engineer periodically updates review rules. Joshi is explicit that this is a manual process in the system described. A proposed investigation agent that might help with the maintenance is future work, not an already running self-improvement loop.

One correction concerns a column whose upstream source is personal information but whose ingestion path encrypts it before writing to the lake. A reviewer accepts a different downstream classification for that particular pipeline. Joshi warns against turning the example into “encrypted means non-sensitive” as a universal rule. The relevant context is the specific transformation and policy.

At 00:20:14, the quality check has two sides: bad changes incorrectly approved, and fine changes unnecessarily escalated. Sending everything to a human avoids some misses but does not solve the review queue. Joshi reports a miss rate of about 2% as of August 31, 2026, mostly attributed to gaps in the rules. He does not supply a clean, single false-escalation rate. The dominant cause he identifies for those cases is missing context, such as the encryption example.

Those are different repairs. A missed class of dangerous change calls for another check or rule. An unnecessary escalation may call for making relevant context available, not lowering the threshold until the reviewer stops complaining.

The retagging example illustrates a miss. Some columns move from an open copy of the data into a restricted copy after being classified as personal information. The PR looks fine, but a downstream reader still points at the old copy. When the columns disappear there, that reader breaks.

The resulting rule is specific: when a column is retagged as sensitive, search for consumers still reading it from the copy that will lose it. The system improves by recording a relationship it failed to inspect, not simply telling the reviewer to be more careful. Joshi treats this as a missing rule rather than claiming the model spontaneously learned a new policy from the incident.

0:23:22 ↗

Review got lighter, not human-free#

At 00:23:22, Joshi returns to the running schema-change example and then presents aggregate results, again dated August 31, 2026. He reports that about 60% of data-pipeline PRs merge without human review, manual review effort is down about 75%, the time saved is roughly 132 engineering hours per month, and incidents tied to those PRs are down about 30%.

Complete official recording, 00:24:07. The slide dates these results to August 31, 2026 and explicitly retains human review for sensitive grants, migration intent, and low-confidence cases.

These are results reported by the speaker for the data-pipeline review system, not an independent causal evaluation or a statement about all Robinhood pull requests. The distinction between the first two numbers matters. Avoiding human review on some changes is one source of savings; giving people specific comments and an evidence chain makes the remaining reviews less expensive too. The system does not have to remove every reviewer to reduce the queue.

Nor do protected categories disappear when the aggregate numbers look good. Sensitive-data access, changes in meaning, and uncertain verdicts continue to reach people by design. “No human review” describes a subset of PRs, not an absence of human ownership over the system or its policy.

0:24:20 ↗

The architecture still has a blind spot between its two halves#

The recovered ending includes an important admission at 00:24:20. Layer one and layer two are separate systems, independently triggered and running in parallel. Each produces a result, but neither sees the other's actual pass, fail, or outage state. The agent knows what the scripts are configured to cover, not what happened when they ran for this PR.

Merge still requires both passing checks and an approving review. That gate remains intact. The limitation is that no single component has the complete runtime picture. The agent cannot request a live check when its reasoning discovers that it needs one, because its tools only read and search repository files. If one side cannot finish, the system waits for a person; there is no automatic fallback.

This qualifies the otherwise appealing division of labor. Separating facts from judgment keeps responsibilities clear and avoids asking an LLM to rediscover authoritative answers. Separating the implementations so completely that they cannot exchange runtime evidence also creates work for people.

0:25:21 ↗

A proposed shared entry point, not a shipped improvement#

At 00:25:21, Joshi shows the direction the team is exploring. One entry point would see the whole PR. A classifier would decide which changes should be reviewed separately and which belong together. That is a whole-PR decision, not a rule that independently routes each changed file and ignores relationships between them.

The agent would also receive the layer-one checks as callable tools alongside repository search. If a judgment required a live fact, it could ask the appropriate authoritative check rather than remain limited to the code.

Complete official recording, 00:25:57. The slide is explicitly labeled “Proposed — not built.” The classifier sees the whole PR, and the agent would gain callable live checks.

Joshi is explicit that this design is not built. It is motivated by limitations in the current system, not included in the performance results he has just shown. That distinction prevents the talk from turning an architectural sketch into an explanation for already measured improvements.

His closing lessons return to the three responsibilities. Prove inexpensive facts deterministically. For protected changes, let the agent flag the risk but never clear it on its own. Count false escalations as well as misses, because a reviewer that sends everything to people has only moved the queue.

The answer to “who reviews the bots?” is therefore not another bot acting alone. Scripts establish what their sources can prove; an agent investigates the context those sources miss; people retain the decisions that require their authority. The full ending preserves both sides of that result: review becomes lighter, while accountability remains explicit.
