Building a Safe Software Factory

A coding agent makes it easier to produce a pull request. That does not settle whether the change should merge, whether it behaves correctly after deployment, or whether a vulnerability discovered next week changes the answer.

Andrew FinchSonarStaff Software Engineer

Day 1 livestream · 3:10:06–3:24:30 on YouTube. The player starts and stops at this session’s boundaries.

Introduction#

A coding agent makes it easier to produce a pull request. That does not settle whether the change should merge, whether it behaves correctly after deployment, or whether a vulnerability discovered next week changes the answer.

Andrew Finch organizes those different questions into four verification loops. The factory is more than the agent that writes code, and confidence has to be built at more than one point in its operation.

3:14:17 ↗

Automation follows the next bottleneck#

Finch begins with the familiar development cycle: requirements feed planning, code becomes a pull request, review and CI precede a merge, deployment exposes the result to users, and feedback becomes the next input.

When writing the code gets faster, review becomes a more visible bottleneck. As review is automated, attention moves to deployment, monitoring, triage, and planning. Finch's concern is that connecting those automated stages can also connect their mistakes. Each needs a way to check the work rather than merely pass it onward.

His four-loop framework separates PR checks, post-deployment verification, maintenance, and knowledge. They answer different questions, so adding one does not make the others redundant.

3:17:30 ↗

The merge gate should consume evidence#

The first loop starts with a pull request, runs checks and review, and lets the author or agent respond to findings. When a fix arrives, relevant checks run again. That is already familiar, but Finch argues that review can inspect more than the changed lines.

The 3:17:30 source slide shows several kinds of evidence converging on a decision about the same change.

Some checks ask whether the implementation works. Others ask whether it satisfies the ticket, follows team conventions, conflicts with another open PR, or breaks a consumer in a different repository. Security review looks for vulnerabilities, secrets, and dependency issues. End-to-end validation exercises the running application. Risk assessment estimates the consequences of a mistake.

The distinction between a check running and a useful result matters. A green job name alone does not explain which findings were considered, what risk was accepted, or whether the intended behavior was tested. Finch wants the merge decision tied to recorded evidence and criteria the team controls.

That allows different handling for different risks. A well-understood low-risk change might qualify for automatic approval or merge, while a consequential change still receives human attention. The goal is to spend review capacity where it adds judgment rather than make every PR follow the same manual ritual.

3:19:05 ↗

Deployment creates evidence a branch cannot supply#

The second loop begins after deployment. Logs, traces, and metrics reveal whether the software behaves as expected in its real environment. A pre-merge test cannot fully substitute for that observation.

Finch describes experiments with agents that help evaluate rollouts, decide whether to widen or stop them, and investigate incidents. He is explicit that this area is still developing. The talk proposes where verification belongs; it does not show that an agent can safely control every production rollout without limits.

A failure here also needs a path back to corrective work. Detecting an error without linking it to diagnosis, rollback, or a fix leaves the factory's feedback loop incomplete.

3:20:06 ↗

Maintenance catches changes in the world and in the whole codebase#

The maintenance loop runs alongside feature development. It periodically scans existing code and opens remediation work when it finds a problem.

This catches issues that could not have been found in the original PR. A dependency vulnerability may be disclosed after merge. A new rule may encode something the team has only recently learned. Duplication or complexity may accumulate gradually, with no single change looking alarming on its own.

The unit of inspection changes from a diff to the current codebase. That is why a repository can need maintenance even if every original PR passed the checks available at the time.

Knowledge should improve the next pass#

The fourth loop gathers product intent, business decisions, documentation, lessons from review, and lessons from incidents. Finch emphasizes curation: agents need useful knowledge, not an indiscriminate pile of historical text.

That knowledge can feed every other loop. A coding agent that understands an important constraint may avoid the error in its first implementation. A reviewer can recognize a past failure mode. An incident investigation can start with a known design decision rather than rediscovering it.

The return is fewer repeated review laps and less reliance on a person remembering the same exception each time.

People still choose what the factory should trust#

Finch does not end with a claim that the lights can go out. Humans still audit risky changes, inspect verification evidence, handle exceptions, review architecture, and supply the reasons behind product decisions.

They also design the factory itself: which signals initiate work, what counts as sufficient evidence, what authority automation receives, and when the system stops for help. Faster code production makes those decisions more important. A safe factory is not simply one with more agents checking each other; it is one whose checks correspond to the failures the team actually needs to prevent and detect.
