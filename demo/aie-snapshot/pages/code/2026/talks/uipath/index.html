Your Automation Is Overthinking It

A workflow does not need to deliberate about every step.

Chibi VikramUiPathEngineer

Kevin BernsteinUiPathPrincipal AI Solution Architect

Day 1 livestream · 5:52:15–6:07:31 on YouTube. The player starts and stops at this session’s boundaries.

Introduction#

A workflow does not need to deliberate about every step. UiPath's Chibi Vikram and Kevin Bernstein make that case by placing fast model decisions inside otherwise explicit automation. Their examples move from fraud investigation to document reranking to mailbox classification, but the design question stays the same: which parts require judgment, and which parts should remain ordinary control flow?

5:52:15 ↗

Put judgment where it belongs#

At 05:52:15, the talk separates three approaches. Traditional automation follows predetermined steps. An unconstrained agent decides what to do next from its available tools. Orchestration can combine the two, specifying the workflow while reserving particular points for cognitive decisions.

Jev fits into that third approach. It can provide a bounded classification or selection without paying for a full reasoning-and-generation loop at every branch. The benefit is especially useful when many decisions are independent and can run in parallel. This is not an argument that all agents are unnecessary; the demonstrations repeatedly escalate harder work to a more capable agent and then return to the structured flow.

5:55:59 ↗

A fraud investigation with an explicit escalation#

The first demo, beginning around 05:55:59, starts with a reported anomalous transaction of $48,000. A Maestro workflow retrieves sixty recent transactions and asks Jev to assess them independently. Four are flagged in the example. In parallel, another decision asks whether the available evidence is sufficient to resolve the main case.

It is not. That answer activates the more expensive investigation path rather than forcing a premature conclusion. An agent queries a bank API and finds additional information about the payee account and phone history. The workflow then reassesses the evidence. Its combined result is a high fraud score, followed by a proposed handoff for a person to review the logs and decide whether to freeze the account.

The important unit is the escalation policy. Fast decisions screen the surrounding transactions and determine whether more investigation is needed; a more capable agent gathers missing evidence; the workflow recombines the results. The demo is not evidence that a bank account was actually frozen, nor that every fraud investigation can be reduced to the illustrated score. The presenters report a fiftyfold speed improvement and 7.1-fold cost improvement for their comparison, which should be read as results for the shown workflow.

5:59:00 ↗

Reranking becomes a tournament#

At 05:59:00, the problem changes to retrieving the right document chunks for an agent's context. The team gives an agent an evaluation set and access to three decision APIs, then lets it search for a better reranking strategy overnight. Bernstein describes about fourteen hours of experimentation.

The resulting strategy is a tournament. Candidate chunks compete in groups; stronger candidates advance; a final round establishes their order. The architecture matters because the work within a round can be parallelized. Instead of assuming one large model call must compare everything at once, the system composes many small decisions into a ranking process.

Original stream, 6:02:30. The slide shows hybrid retrieval feeding a tournament in which chunks advance through successive rounds.

The presenters report improved evaluation quality alongside a roughly fifteenfold speed improvement. Their claim is not that tournaments are inherently the best retrieval algorithm. The useful demonstration is that inexpensive decision calls change the search space available to the engineer and to the agent optimizing the system. An architecture that would be extravagant with slow calls becomes practical when many comparisons can finish in parallel.

6:04:00 ↗

Use a language model to invent the categories, not classify every email#

The final example, around 06:04:00, separates taxonomy design from runtime classification. An LLM proposes an initial set of about fifteen mailbox categories. Jev classifies the emails, and the distribution of those classifications exposes categories that are too broad, too narrow, or scarcely used. The LLM revises the taxonomy, and the system classifies again.

Cheap repeated passes make this feedback loop feasible at a scale the speakers describe in terms of a million emails. Once the categories fit the mailbox, the runtime path no longer needs the LLM that invented them: an incoming message gets classified, and deterministic automation routes it to the appropriate team or notification.

This is a form of distillation into workflow structure rather than model weights. Expensive reasoning designs the categories and the process; inexpensive decisions operate it. The talk closes without claiming that these patterns are settled. Its examples are an invitation to look for repeated judgments inside existing automation, preserve the places where deeper investigation is valuable, and stop asking every routine branch to think from scratch.
