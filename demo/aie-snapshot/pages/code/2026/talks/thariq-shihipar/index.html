Keep the human inside the creative loop

Introduction#

Thariq Shihipar starts with predictions he got wrong. Agents did not settle into one permanently correct tool interface. Work he expected to stay inside familiar web frameworks expanded into other languages and applications. Capabilities kept moving beyond the boundary he had drawn around them.

That history makes him wary of treating today's workflow as destiny. Better models can do more, but it does not follow that people should surrender every part of making software that they enjoy or understand. His talk asks what the human experience of building should become as the machine's contribution grows.

Capability does not dictate one interface#

Shihipar contrasts the uneven frontier of what a model can do with the large interior of tasks it can already perform in multiple ways. At the frontier, a particular technique may be necessary to make something work at all. Inside that boundary, there is more freedom to choose an interface around human needs.

He also explores the hypothetical endpoint of a model that performs a task perfectly. In that hypothetical world, some verification work would no longer be necessary. He is not claiming current coding agents have reached that point. The thought experiment is a way to separate enduring human goals from compensations for current model limitations.

This changes the design question. Instead of asking only how to squeeze another task through the present agent interface, ask what a better interaction would feel like once the model is capable enough to support it.

The agent can finish the move and still lose the player#

His concrete example is a two-dimensional fighting game inspired by familiar action and elemental-combat ideas. He asks an agent to implement a rock throw. The agent fills in many details: how the projectile moves, how large it is, how it charges, and what it collides with.

The feature exists, but the creator no longer understands all of the character's behavior. Decisions that determine the feel of the game have been made at a distance. Waiting for the agent also interrupts his concentration. The problem is not just whether the generated code runs. It is whether the workflow lets him remain engaged in shaping the game.

One answer would be to accept that distance as the inevitable price of automation. Shihipar instead changes the boundary between agent work and human work.

8:52:35 ↗

Let the agent build the primitives#

The game can have an engine layer that the agent largely owns and a more readable layer where the designer edits behavior. The latter should expose meaningful concepts and units rather than force every creative adjustment through a large implementation request.

At 08:52:35, Shihipar shows the game project and its behavior code. The screenshot documents the live editing surface; the small source text is not reproduced as a verified code listing.

His examples include the properties and origins of the rock attack. Changing its size or behavior should be a direct, legible operation. The agent can help construct the primitives and support completion in the editor, while the human stays close to the effect of each adjustment.

This is a different division of labor from asking for a whole feature and reviewing the finished diff. It uses the model to create an environment in which a person can make many small decisions quickly. The value is not only fewer keystrokes. It is preserving the continuous connection between intention, experiment, and response.

Rules and structure help maintain that boundary. The human-readable layer should describe what actually happens, rather than become a second specification that drifts away from the implementation. The abstraction earns its place by making the game easier to shape.

Better automation can make room for more craft#

Shihipar presents this as an experiment, not a completed universal method. Other domains may need different primitives and different editing surfaces. Better models may make new languages, databases, servers, or operating-system interactions practical. The human-computer interaction problem remains: which decisions should be immediate and visible to the person doing the work?

His broader analogy joins cheap production with renewed attention to quality and craft. If generating an implementation is less scarce, the experience of choosing, refining, and understanding can become more important rather than less.

That is the sweet side of his argument. The lesson of improving models need not be that every person becomes a supervisor waiting for opaque batches of work. It can also be that we have more freedom to build tools around the parts of creation people want to do. The model's growing capability supplies the material. The interface determines whether the human still gets to play.
