Choose the project you can verify

Jarred Sumner wanted Claude Code to use less memory and run faster. One possible answer was to rewrite it in Rust. He had experience with that kind of rewrite, but the tests changed the decision.

Introduction#

Jarred Sumner wanted Claude Code to use less memory and run faster. One possible answer was to rewrite it in Rust. He had experience with that kind of rewrite, but the tests changed the decision.

Bun's tests were written in TypeScript and could exercise different implementations of the runtime. Rewriting Claude Code itself would also mean porting its tests. The new implementation and its supposed source of truth would move together. Sumner instead pursued a way to make the existing JavaScript faster: an ahead-of-time compiler for Bun.

The talk is a story of repeated compiler rewrites, but its governing question comes first. What evidence would let you trust the result of a project written at agent scale?

Move compilation out of the running application#

A just-in-time compiler does compilation work while the application runs. An ahead-of-time compiler pays that cost before execution. Sumner presents this as particularly attractive when many instances of a JavaScript application otherwise repeat that work.

He reports lower memory use and faster startup in the project under development. Those are results from his described workload and benchmark set, not a guarantee that every JavaScript program receives the same improvement. Later in the talk he points out workloads involving dynamic evaluation that do not benefit in the same way.

TypeScript adds another opportunity and another risk. Its annotations are not guaranteed to describe runtime values correctly. The compiler treats types as predictions rather than blindly trusting them. Where it can establish a stable property access, it can specialize; elsewhere it must preserve checks.

5:25:51 ↗

Reuse tests that predate the implementation#

At 05:25:51, Sumner explains why this problem suits agent-driven work. The compiler can be checked against existing Bun, WebKit, language-conformance, and application tests. Bun's own test runner can also run in ahead-of-time mode.

At 05:27:10, the slide distinguishes tests matching the JIT from refused and different outcomes. That distinction matters more than treating a large test count as a blanket correctness claim.

Differential testing supplies another check. Run an application with the JIT, ahead-of-time compilation, and a version without type information. Agreement is evidence for that application. Fuzzing then generates more cases that can expose disagreements.

The independence of the oracle is the important property. If an agent rewrites the implementation and the expected answers together, passing tests can become circular. Existing tests and comparisons against another execution path make that harder.

Even then, test infrastructure needs testing. A fuzzer that reports no bugs may be doing an excellent job, or it may fail to exercise the behavior that matters. Sumner stresses checking whether the tests actually catch faults rather than trusting the presence of a test command.

5:28:02 ↗

Different phases need different parallelism#

The implementation story moves through several rewrites. One version used too much memory. Another improved performance but contained brittle special cases. A later version had better code but unacceptable compilation time for users accustomed to JavaScript's fast start.

A project can therefore pass one evaluation and still fail the product requirement. Runtime performance, implementation quality, build time, and usability all need to stay in view.

Sumner separates a large initial code-writing phase from the repair phase. During the first, running a full build after every partial edit can spend most of the time compiling an incomplete system. Once the initial structure exists, many focused agents can work on individual failures.

For sustained work, he increasingly favors long-lived subagents. They keep relevant code context rather than repeatedly rediscovering the subsystem. This is an operational choice about continuity, not a claim that maximum concurrency is always optimal.

5:40:09 ↗

Keep measuring while the agent keeps improving#

An hourly scorecard helps Sumner follow a project too large to hold in his head. Measurements compare earlier and current versions, so a claimed improvement can be checked against regressions elsewhere.

The benchmark discussion preserves exceptions. Ahead-of-time compilation is not uniformly faster, especially when dynamic code forces execution down less optimized paths. The compiler also makes deliberate compatibility restrictions, including restrictions around modifications to built-in objects; performance and security motivations do not erase the need to account for those changes.

What remains for the human? Sumner describes asking leading questions, challenging estimates, and refusing to let a model talk itself into small goals. He also rejects generated design-document volume as a substitute for understanding the implementation.

The ending joins ambition to verification. Agents can attempt a large rewrite because the project has strong ways to compare behavior. Those checks must keep running as the code changes. Without them, an impressive initial result can quietly deteriorate while everyone watches the next feature arrive.
