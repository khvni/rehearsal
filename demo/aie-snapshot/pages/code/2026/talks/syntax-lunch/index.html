The code still needs someone who cares

Scott Tolinski and CJ Reynolds spend their lunch session moving from state machines to programming languages, native applications, skill loss, and a game about identifying model-generated interfaces.

Introduction#

Scott Tolinski and CJ Reynolds spend their lunch session moving from state machines to programming languages, native applications, skill loss, and a game about identifying model-generated interfaces. Under the news and jokes is a consistent question: what does engineering judgment look like when an agent writes most of the implementation?

Their first example is a prompt asking an agent to find implicit state machines. It sounds small. It points toward a much larger role for the developer: choosing representations that make bad behavior harder to express.

Turn scattered flags into a model of the state#

A UI can accumulate independent flags for loading, errors, and success. Without a coherent model, combinations appear that the product never intended. The hosts contrast that with explicit states and transitions, where the permitted behavior is centralized rather than distributed across unrelated conditionals.

The benefit is not merely cleaner code for humans. A constrained representation also gives the agent fewer opportunities to introduce contradictions. Reynolds connects this to a second prompt: look for duplicated behavior and opportunities to consolidate it.

His concrete example is file access. A CLI had multiple paths for reading and writing files. Consolidating them behind a file manager would mean little if the agent continued to add direct filesystem calls. A lint rule prohibiting those calls makes the abstraction enforceable. The developer chooses the boundary; automation keeps subsequent changes inside it.

This is the session's first answer to the idea that code quality no longer matters. A codebase is part of the next agent's working environment. Its structure can help or hinder future changes.

Cheaper implementation reopens old choices#

The news discussion then moves through app modification and control over one's own software before arriving at languages and frameworks designed with agents in mind. The hosts acknowledge an intuitive objection: why would a model be good at a language that was absent from its training data?

Their experience with examples and documentation has made that objection less decisive. A repository of patterns, current documentation, and tools exposing the framework's state can help an agent work in a less familiar environment. They discuss explicit errors, schemas, and centralized state as properties worth considering alongside familiarity.

That is not a blanket recommendation to adopt every new language. The hosts joke about the volume of new releases and the difficulty of knowing which will matter. Their argument is that the cost of writing unfamiliar syntax is no longer the only factor in selecting a stack. A representation that makes correctness easier may deserve another look.

The same reasoning leads into native desktop applications and Rust UI frameworks. They discuss reported rewrites and the attraction of lower resource use, while also remembering why Electron became popular: predictable browser behavior and cross-platform distribution. They explicitly wonder how an application's existing tests survive a migration. The conversation leaves that question open rather than treating an impressive rewrite as proof that all portability problems are solved.

Losing a skill is not the same as losing judgment#

Audience questions bring the discussion back to developers. The hosts distinguish skills that become less useful from knowledge still needed to steer work. Remembering obsolete browser hacks is not an enduring obligation. Understanding why an application is slow or why a large codebase needs shared abstractions still matters.

They also recognize the organizational pressure behind skill anxiety. Teams told to use AI and move faster may become too exhausted to evaluate what they are learning or forgetting. Calling the change inevitable does not settle whether a particular workflow is good.

Their example of duplicated desktop and mobile DOM trees makes the distinction concrete. A page may appear to work and score acceptably on a convenient metric while retaining an unnecessarily poor implementation. Someone still has to notice that and care enough to change it.

The term “vibe coding” proves less useful than this underlying question. The hosts disagree about how broadly to use it, but reject dismissing every AI-assisted project as worthless. They also reject output that shows no editing, taste, or responsibility. The presence of AI is not the same thing as the absence of care.

A guessing game is not a benchmark#

The session's game shows pairs of generated buttons, flyers, and inboxes and asks which model made each. Guesses rely on gradients, typography, emojis, and how much unwanted material surrounds the requested element. Several guesses fail. Some outputs do not even respect the request for a single button.

The segment is entertainment, not a controlled model evaluation. Its useful observation is that brand expectations and visual stereotypes are unreliable substitutes for inspecting an actual result. A polished-looking artifact can still miss the request; a model someone rarely uses can produce the preferred design.

The closing audience question asks why anyone should release an app when copies are so cheap. The hosts return to care: documentation that explains the product, thoughtful interactions, and polish in small corners all give users reasons to stay. An app is more than a screenshot or a repository link.

That ending connects back to the opening state-machine prompt. Engineering judgment can operate deep in a representation or in the smallest visible interaction. Agents reduce the cost of implementation, but the developer still decides which outcomes deserve attention and which shortcuts impose work on the next person. The session's durable advice is to keep making those decisions deliberately.
