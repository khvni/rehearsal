cloudflare is a neolab

Cloudflare built a distributed inference network around a bet: models would get smaller and faster, making the distance between the model and its user increasingly important.

Michelle ChenCloudflareGroup Product Manager

Day 1 livestream · 0:40:09–0:59:44 on YouTube. The player starts and stops at this session’s boundaries.

Introduction#

Cloudflare built a distributed inference network around a bet: models would get smaller and faster, making the distance between the model and its user increasingly important. Instead, the frontier moved toward larger models. The company adapted to serve them, but Chen says the fit with its original infrastructure still felt incomplete.

Her talk follows the route from that mismatch to training decision and extraction models. The interesting part is the workload that brought the small-model hypothesis back, and how it changes an ordinary agent loop.

0:42:44 ↗

A CDN becomes somewhere to run the application#

Chen starts with Cloudflare's origins as a content delivery network. A CDN sits between the user and the origin server, bringing cached content closer and adding protection along the way. That requires distributed infrastructure rather than putting everything into a few centralized regions.

The next question was what developers could do with computers already close to their users. Workers exposed short-lived serverless computation. Durable Objects added stateful coordination; containers accommodated workloads that needed a different execution environment. Storage products supplied the other half of an application: key-value data, object storage, and databases.

This history matters because the AI proposition was not an isolated model API. Chen describes an agent running on Cloudflare compute, interacting with Cloudflare-hosted data, and invoking models on the same platform. Model serving had to make sense as part of that developer experience.

0:47:55 ↗

The small-model bet returns as a decision problem#

Workers AI added GPUs to the network in 2023. Chen describes the original expectation as small models becoming more useful while network latency became a larger fraction of response time. Larger models pushed the product in a different direction. Cloudflare learned to serve those too because they belonged in the application platform, even when they did not fit the original edge-inference story as neatly.

At 00:47:55, the story changes with TypeSafe's Jev and the idea of a fast decision model. Instead of asking an autoregressive model to generate a reasoning trace for every small choice, a specialized model can return a decision directly.

Chen treats those models as complements to generative LLMs. Some tasks need open-ended reasoning or generation. Others need a quick choice from a defined set. Moving the latter off the large model reduces work, latency, and the amount of context sent through the expensive part of the system.

The infrastructure fit reappears: if inference itself is short, a long network journey is no longer a negligible addition. Cloudflare could not host the closed Jev model directly, so Chen recounts the team's decision to build its own approach. The resulting decision model is Clef, whose spelling is visible on the source slides.

Extraction gives the next stage typed inputs#

A decision model still needs usable data. People send emails, messages, and documents, not perfectly typed arguments to a function.

Chen introduces Claric as a second piece: turn unstructured inputs into typed values an application can use. In her description it can extract, compute, estimate, and forecast values; those are different tasks with different correctness requirements, even when the output shares a JSON shape. A typed result makes integration easier, but it is not by itself proof that every extracted value is right.

The proposed division of work is straightforward. Extract the relevant fields, decide what to do with them, and reserve the larger model for the work that still needs generation or broader reasoning. The model sequence is embedded in ordinary code rather than requiring an LLM to narrate every transition.

0:54:08 ↗

Stop sending all forty tools on every round trip#

The developer-workflow example investigates a failed CI build. The baseline gives an LLM forty tools and lets it iterate: choose a tool, receive a result, choose another tool, repeat. Tool definitions and raw results repeatedly enter the context.

Chen reorganizes the same job into a narrower pipeline:

  1. Select relevant tools. Clef Flash prunes the available set from forty tools to ten.
  2. Fill the arguments. Claric extracts values such as the pull-request number instead of spending a generative round trip on them.
  3. Execute in code. The application invokes the selected APIs with those arguments.
  4. Read the logs into fields. Claric extracts the error and affected code information, instead of handing over hundreds of raw log lines.
  5. Ask the LLM for the final work. The larger model receives a smaller, more focused problem.

At 00:55:30, the slide shows one round trip to the generative model, ten selected tool schemas, and six typed log fields rather than the raw log.

The benefit is not simply that a smaller model runs faster. The application removes repeated deliberation over steps it can structure explicitly. It also avoids making every intermediate result part of the LLM's next prompt.

Chen runs the two paths together and reports that the specialized path finishes first while reaching the same answer in that demonstration. She also describes an earlier run without conference Wi-Fi that took 9.2 seconds versus 17.2 seconds, with lower cost and token usage. Those are results for the presented CI workflow, not a guarantee that the same reduction will transfer unchanged to a different tool set or task.

Build around the kind of work, not one model category#

Chen closes with other places this division could fit: routing, spam or phishing decisions, and extracting data from support tickets or web pages. The shared question is what the application actually needs back. A constrained decision, a typed field, and a generated explanation should not automatically receive the same implementation.

Her retrospective is also a warning against turning infrastructure strategy into a fixed prediction. Cloudflare adapted when large models dominated, then adapted again when fast specialized workloads made its distributed network valuable in a new way. The practical invitation is to inspect your own agent's repeated reasoning steps. Some may be genuine judgment. Others may be a function, an extraction, or a bounded choice waiting to be separated out.
