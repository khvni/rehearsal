What it takes to set intelligence free

Introduction#

Lovable nearly failed by building for agents too early. Fabian Hedin opens with that admission, not with the architecture diagram. In 2023, the team could see a future of agents delegating to agents, but the models available at the time could not reliably support the elaborate system they built around them.

His account of Lovable's current platform is therefore a story about timing as well as infrastructure. Better models make longer-running work possible, but the surrounding system still has to preserve state, supply a usable computer, and tell the agent whether its work is actually succeeding.

7:27:13 ↗

The beautiful architecture that made the product worse#

At 07:27:13, Hedin recalls the early GPT Engineer product: chat on one side, a preview on the other, and essentially one model call per user message. It could build relatively simple applications. The team then introduced a sophisticated multi-agent framework with implementation, frontend, and backend specialists exchanging messages.

The result was worse. Before the company ran out of money, Hedin says, it returned to a simpler system: small models helped retrieve knowledge, while one main model wrote the response and code. The product became more responsive and reliable. Users could stay involved in the iteration rather than waiting for an ambitious architecture to coordinate itself.

Hedin now argues that the intelligence has caught up. He describes the newer system operating at more than a billion tokens per minute, a scale claim from the presentation rather than an independently audited measurement. The visible interface remains deceptively similar: a person expresses intent and sees an outcome.

The outcome is a business, not a pile of code#

Before the technical details, Hedin explains why Lovable supplies more than a coding agent. The agent has a browser and GitHub integration, but it also has access to hosting primitives: databases, authentication, storage, compute, logs, backups, and security tools. These capabilities are designed to be inspectable by the agent rather than assembled manually across unrelated services.

The next layer concerns operating the product: payments, email, SEO, advertising, analytics, and conversions. Hedin's point is that users ultimately want a useful product or business. Writing code is one activity inside that objective.

Longer tasks make this broader scope consequential. Lovable once limited an agent to thirty minutes because it did not trust longer execution. Hedin describes removing that fixed duration limit and supporting work lasting ten hours or more. Three systems must cooperate: the runtime, the computer, and verification.

7:34:56 ↗

Preserve the history; render the prompt#

At 07:34:56, Hedin starts with an inbox for each agent. People, other agents, or scheduled systems can send messages. The running agent incorporates those messages into its trajectory when it reaches an appropriate point between actions.

That trajectory is an append-only event history inspired by Git. Each event points to a parent, making it possible to fork from a shared past without copying all preceding events. Hedin is explicit about the limit of the analogy: the system can fork agent histories, but it does not have a clear semantic operation for merging them like source-code branches.

Original stream, 7:36:40. Two continuations point back to a common event in Lovable's task history.

The history is also separate from the prompt sent to a model. Tool calls, successes, failures, and other events remain recorded; the system renders an appropriate prompt from that record. Different models can use different compaction strategies and context lengths without forcing the stored task history to become a lossy summary.

Separating the executing process from that history lets processes come and go. Hedin reports roughly seven hundred deployments per day. A ten-hour task cannot depend on the same process surviving all of them, nor should a long-running task prevent urgent updates. Persisting between turns lets a newer process continue the same work.

7:40:13 ↗

Give the agent a computer that can resume and fork#

The second layer begins at 07:40:13. A golden checkpoint includes the operating system, services, tools, development server, disk, memory, and running processes. Hedin reports starting from it in about 230 milliseconds. Project-specific state is checkpointed as work proceeds, allowing idle computers to stop and later resume quickly.

The same mechanism supports forks for separate drafts or parallel explorations. Copy-on-write memory keeps the initial fork cheap: pages need additional allocation only when modified. Streaming memory allows the machine to start before every page has arrived from storage. These optimizations address different costs, memory duplication and startup latency, rather than treating “sandbox speed” as one opaque number.

Lovable also took control of part of the software inside the sandbox. Hedin describes rewriting its Vite-based development-server path in Rust, reducing the memory footprint and speeding preview startup. His reported preview improvement is from fourteen seconds to three, with a 6.5-fold smaller memory footprint. Controlling memory writes also makes copy-on-write forks more efficient. The point is that agent infrastructure includes the applications running in the computer, not just the VM boundary.

7:45:23 ↗

Verification has an inner and an outer loop#

At 07:45:23, Hedin distinguishes feedback within a turn from feedback between turns. The inner loop includes builds, lint and type errors, runtime errors, and browser exploration. It tells the agent whether its immediate implementation works.

The outer loop concerns the product after people use it: visitor behavior, feedback, A/B tests, conversions, and business metrics. Access to payments and analytics matters because those systems can supply evidence about the outcome the user actually wanted, not just whether the code compiled.

Hedin closes by returning to the architecture that once failed. Agents can now talk to other agents and explore work in parallel, supported by persistent histories, cheap resumable computers, and feedback. The claim is not that complexity was right all along. The earlier simplification saved the product; the newer capabilities make a more ambitious system useful now. The user should still encounter a simple interface, while the platform does the work of keeping a long-running agent grounded in its task and its results.
