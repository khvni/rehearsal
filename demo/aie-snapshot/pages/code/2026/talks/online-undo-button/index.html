An Agent's Change Is Not Safe Until Its Recovery Has Been Tested

The coding agent has done what it was asked to do. It patched the repository, passed the tests, and produced a release. Then a downstream integration fails. Reverting the Git commit sounds like an obvious response, but the repository is only one part of the system the agent changed.

Introduction#

The coding agent has done what it was asked to do. It patched the repository, passed the tests, and produced a release. Then a downstream integration fails. Reverting the Git commit sounds like an obvious response, but the repository is only one part of the system the agent changed.

An API call may already have created a ticket. A runtime setting may have changed. A notification cannot be unsent by restoring a source file. Tanmay Sah and Dolly Sah use this gap between code rollback and world-state recovery to motivate UndoBench and EvoUndo. Their question is not only whether an agent can finish a task. It is whether the agent can recover when its actions have partly succeeded and the feedback has failed.

4:27:26 ↗

A timeout is not proof that nothing happened#

The first example is a ticket-creation request. The service commits ticket 781, but the acknowledgment disappears before reaching the agent. From the agent's perspective, the request timed out. From the service's perspective, the ticket exists.

Retrying the same operation can create a duplicate. The problem is not an agent forgetting how to call an API. It is an agent confusing missing evidence of success with evidence of failure.

At 04:27:26, the speakers describe UndoBench's 2,880 paired trials. They report 84% success on ordinary task execution, but recovery in only 47% of the trials that had succeeded under normal conditions. The denominators differ: the recovery percentage is conditional on normal success. They also report duplicate effects in 54% of the relevant retry trials. These are results of their evaluation, not a universal failure rate for coding agents.

The timing of a failure determines the safe response. Before a mutation, retrying may be appropriate. During a mutation, the system needs to inspect partial state. After a committed mutation with a lost acknowledgment, it needs to discover the committed effect before taking another action. An undifferentiated retry policy erases those distinctions.

Recovery needs evidence from before the change#

A repository snapshot is insufficient when an agent operates through tools, middleware, deployment systems, databases, or runtime configuration. The speakers extend this observation to self-modifying agents. Changing prompts, tools, listeners, resources, or routing can increase capability while quietly reducing recoverability.

Consider changing a timeout from 30 to 60. An instruction to restore the old value is useless if the old value was never recorded. The system needs a pre-state witness: evidence of the relevant state before the mutation. Recovery then has an explicit target instead of an agent's best guess about what probably used to be true.

Capturing evidence is necessary but not sufficient. The agent also needs a recovery language expressive enough to reverse or compensate for the effect. Knowing exactly what changed does not help if the only available recovery operation is a crude rollback that cannot address that kind of change.

4:34:24 ↗

Capability improvements can introduce recovery defects#

In the EvoUndo experiment, the speakers report 600 self-evolution tasks and 478 capability-improving candidates. Of those improvements, 197 introduced recoverability defects. Improving forward performance therefore did not establish that the new system was safe to admit.

At 04:34:24, they separate two bottlenecks. One is state grounding: does the recovery process know what actually changed? The other is expressivity: can it describe and execute the recovery that is needed?

Their reported probes use different subsets. Providing precise changed-state information moves one probe from zero recoveries to 38 of 48. Providing richer undo operations moves another from zero to 142 of 143. Those numbers should not be added together or treated as measurements over the same denominator. They diagnose different limitations.

The broader result they present is recovery of 180 of the 197 defective improvements using a richer recovery language. The number of admissible improvements rises from 281 to 461 out of 600. The point is not that every effect has become reversible. It is that recovery failures can arise from missing machinery, and that machinery can be evaluated independently of the capability improvement.

4:38:00 ↗

Make recovery an admission test#

The slide at 04:38:00 makes the decision explicit: propose, record, test, independently verify, then admit or repair/reject.

Dolly Sah describes the procedure as a gate around a proposed mutation. The candidate arrives with an effect contract and a recovery plan. The system captures pre-state evidence and receipts, applies the mutation in a test environment, and executes the proposed recovery. An independent verifier checks whether the recovered state matches the original state for the effects being tested.

Only a candidate that passes both capability and recovery criteria is admitted. A failed recovery sends the candidate back for repair or causes it to be rejected. This changes the role of undo from an emergency action after deployment to a property tested before deployment.

The slide's own limitation is important: empirical state-equivalence checks are scoped to evaluated effects and sampled states. They are not a proof of universal reversibility. A verifier can establish something meaningful without establishing everything.

Retry, restore, compensate, or stop#

The final operational policy has more than two choices. Retry when the system can establish that the relevant state is unchanged. Restore when the previous state is known and a suitable reversal exists. Compensate when an external effect has already committed and literal reversal is unavailable. Stop or escalate when safe recovery cannot be verified.

That policy turns uncertainty into an input to control flow rather than an invitation to try harder. It also explains why “the tests passed” is an incomplete admission criterion for a self-improving harness. Forward correctness says the new behavior works in the tested situation. Recovery testing asks whether the system still has a controlled way back when something goes wrong.

The missing undo button is not a button. It is evidence captured before mutation, a vocabulary for recovery, and a verifier empowered to reject an otherwise useful improvement.
