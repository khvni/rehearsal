Your Judge Is Hallucinating Too

An agent says it scheduled an email for Tuesday.

Brian KennedyZoomInfoPrincipal Engineer

Day 1 livestream · 6:11:43–6:22:59 on YouTube. The player starts and stops at this session’s boundaries.

Introduction#

An agent says it scheduled an email for Tuesday. The judge accepts the step. But the tool result says the Salesforce record creation failed, and the agent does not even have a tool that can send the email. Brian Kennedy opens with this failure because it exposes a second problem beneath agent hallucination: the evaluator can believe the agent's account instead of the evidence.

6:11:43 ↗

The reassuring story beats the failed tool call#

At 06:11:43, Kennedy walks through a production-style orchestration pattern at ZoomInfo. Specialized agents research, work with CRM data, and carry out other customer workflows. A judge decides whether a step should be accepted, retried, or stopped.

The initial judge was broadly reusable. That was attractive operationally, but it left the model responsible for recognizing what success meant across many different tasks. In the opening example, creating a task was treated as if it satisfied a promise to schedule an email. The tool's explicit failure did not prevent a fluent success narrative from winning.

Kennedy's team assembled five hundred real production steps, used a larger frontier model to regrade them, and had people review the cases and resolve disagreements. Against that reference set, he reports roughly 65% correctness for the existing judge and 118 false accepts. The failure was not just an occasional malformed response. It was accepting work that had not been done.

6:19:00 ↗

Ask narrower questions about the evidence#

One possible response would be to write a custom judge prompt for every workflow. Kennedy rejects that as an expanding maintenance problem. Instead, the team tests a decision model against a fixed set of smaller questions. The input includes the instructions, the tool calls and their results, and the agent's report. The output includes probabilities for accept, redo, and stop, plus seven bounded checks that help explain the disposition and generate useful feedback.

The talk does not enumerate those seven checks in sufficient detail to reconstruct them here. Its architectural distinction is clear: the evaluator should inspect evidence about execution rather than merely assess whether the agent's prose sounds satisfactory.

At 06:19:00, the original email case receives approximately 0% accept, 97% redo, and 3% stop from Jev. Kennedy reports about 0.2 seconds for that decision versus 2.5 seconds for the LLM judge. The team then sets confidence thresholds using the five-hundred-case dataset, routing uncertain cases back to the LLM. Those thresholds belong to this calibration exercise, not a universal recipe for deploying any judge.

A promising offline result is not permission to take over#

For about 70% of the reference set, the new approach is confident enough to decide. Within that subset, Kennedy reports that it catches 74 of 82 bad accepts made by the original judge. That is useful evidence, but the next step is shadow mode rather than immediately transferring control.

Original stream, 6:20:30. Both judges inspect the same steps; only the LLM judge controls the workflow.

The shadow run covers roughly 37,000 verdicts. Kennedy reports 728 explicit tool-failure cases, with the existing LLM judge catching 294 and Jev catching 623. In a separate email-step category of 1,081 runs, he reports one catch by the LLM judge versus 876 by the new approach. These numbers describe the categories and comparison shown in the talk. They are not a claim that every disagreement was automatically resolved correctly.

Shadow mode is central to the argument because it lets the team inspect disagreements without making the experimental judge responsible for customer outcomes. Kennedy also reports a tenfold speed improvement and fortyfold cost reduction. Those gains matter, but they sit beside the more consequential question: which failures does the system now notice, and which does it still miss?

Judge the postcondition, not the promise#

Kennedy ends with a further direction: explicit postconditions for individual tools. If the action was sending a message, was it delivered? If it was writing a record, does that record exist? The presentation describes this as a next step, not an already completed general solution.

That ending sharpens the opening failure. A judge cannot establish delivery by approving the sentence “I sent it.” Nor does a successful-looking substitute action prove the requested action happened. The evidence has to match the task's postcondition.

His recommended rollout remains deliberately narrow: choose one judgment, turn it into bounded questions, run the alternative in shadow mode, and read the disagreements. The talk is not a proposal to replace one unexamined authority with another. It is a case for making the authority of a judge depend on observable work, then testing that dependence before allowing it to control the next step.
